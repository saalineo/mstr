# Benchmarks: mstr vs SDS vs hand-written malloc code

Generated by `bench/bench.c` (`cmake -DMSTR_BENCH=ON`, then `build/bench --md`).

* **Machine:** 11th Gen Intel Core i5-11400H @ 2.70 GHz, Linux, gcc 16.2.1, `-O2`, library built without
  checked mode and with `-DNDEBUG -DMSTR_STATS`.
* **SDS:** upstream `antirez/sds` commit `5347739`, vendored unmodified in `bench/third_party/sds`; only
  `sdsalloc.h` is replaced by a shim that counts allocations.
* **Method:** every implementation is first verified to produce the **same bytes** for each workload.
  `ns/op` is the best of 5 timed batches (300k and 200k iterations) after a warm-up. Three whole-program runs
  agreed within about 10% on every row. `malloc calls` and `bytes` are counted at the allocator
  (hand-written code and SDS through counting wrappers; mstr through `mstr_set_allocator`), over 1000 steady-state ops.
* **Reading the mstr columns:** an *arena bump* is a pointer increment inside a pre-allocated chunk, reclaimed by
  the scope in O(1) with no `free` call. `malloc calls` for mstr counts only fresh chunks, which is 0 once the
  arena is warm. Plain C and SDS pay `malloc` and `free` per op.
* **Inputs are `char *`,** so mstr copies the input once (`mstr_from`, one bump) just as SDS does with `sdsnew`.
  "input is mstr" shows the zero-copy case.

## What the numbers say

* **Allocation counts:** mstr makes **zero** `malloc`/`free` calls per op on both workloads. Hand-written
  step-by-step C makes 3, SDS makes 1 (W1) and 24 (W2), `strdup`-ing C makes 21.
* **Time:** mstr is **not** faster than careful hand-written C. On W1 the fused C loop is about 9x faster and the
  step-by-step version about 4x; on W2 the pointer scan is about 7x faster, and `mstr_each` is slower than the
  version that does 21 `malloc`s. mstr is on par with SDS on W1, faster than it on `mstr_each`, and equal
  on `mstr_split` (both build an array of tokens).
* **Why it is slower than C:** a value is 24 bytes passed and returned through memory, and the operations
  are non-inlined library calls. Costs measured separately: scope enter+leave 5 ns, `mstr_from` of
  110 bytes 14 ns, `trim` 14 ns, one SSO copy about 10 ns, `upper` of 104 bytes 76 ns (a scalar loop at `-O2`),
  `replace_all` of one byte 94 ns. A token costs about 25 ns in the iterator plus about 11 ns for `trim`.
* **`MSTR_PIPE` vs nested calls:** the pipe holds **half** the arena bytes once the chain is done (112 vs 224)
  because each step's result slides down over its dead input. It does **not** reduce the number of arena
  allocations (3 for both) and is about 19% slower because of the extra move. The original brief expected "~1-2
  allocations" for a 3-step chain; this design does not deliver that. See DESIGN.md (M5) for why.

## Things tuned because of this benchmark

The first run had `replace_all` at 352 ns and a per-token iterator cost near 28 ns. Two fixes followed:
a single-byte fast path in `replace`/`replace_all` (352 to about 94 ns), and a `memchr` fast path for
one-byte delimiters in `mstr_each`/`mstr_split`, plus a size-bucketed SSO copy in place of a variable-length
`memcpy`. Hand-written baselines were also corrected: the first version called libc `toupper` per byte, which
made them look slower than they are; they now use the same inline ASCII mapping as `mstr_upper`.

## Not measured

Multi-threaded throughput, strings far larger than a cache line of chunks, UTF-8 operations, checked mode
(it adds a validity check on every access by design), clang, and other CPUs. Treat these as one machine, one
compiler, two micro-workloads.
